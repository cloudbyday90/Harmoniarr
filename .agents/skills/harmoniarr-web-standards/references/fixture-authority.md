# Application-derived fixture authority

Use for acquisition fixtures that fail current ownership or quality checks.
Read docs/CONTROLLED_PROVIDER_AUTHORITY_DESIGN.md and its research/outcome records
from the active repository. The official-source mapping is OWASP action-boundary
authorization, NIST subject/object relationships and W3C provenance; historical
provenance is not current permission.

## Derive authority from inputs

Create controlled metadata and enabled operators with explicit saved quality
preferences. Save monitored-artist policy and call the actual wanted-release and
discovery reconciliation services. Assert exact owners and links before actual
provider ingestion. A monitoring acquisition-profile label alone does not replace
saved quality preferences. Shared requirements retain the strongest current floor;
private sentinels are not fallback consent.

Reuse testing/docker/controlled-provider-authority-fixtures.mjs for packaged
fixtures. Keep metadata inputs, authority setup, worker driving and assertions in
separate ESM modules. Do not manually populate positive wanted/link/candidate
authority or disable production guards to repair a failed fixture.

## Preserve the accepted command

Load the persisted pending run before manually driving a fixture worker. Preserve
its trigger source, candidate/search IDs, counts, safety mode and apply candidate
scope. A diagnostic label must not overwrite recovery origin. Await the returned
completion so advisory tasks and leases drain before teardown; terminal status
alone is not owned completion. Preserve Error/null refusal.

## Separate preflight, worker and external effects

Strict preflight can refuse media before an apply run exists. Prove that refusal
independently. To test the worker's fresh quality check, admit valid task-owned
bytes through the real guard, then restore the rejected bytes before starting the
worker. Do not fabricate a queued run or relax the current quality requirement.
Limit deliberate source changes to disposable files and restore them in finally.

Pair permitted ingestion/queue acceptance with missing wanted ownership, disabled
accounts and saved monitoring revocation after acceptance. Reconcile revocation
through actual services. Observe the real worker, no library writes and no further
provider transfer. This is a post-download apply boundary; it does not establish
pre-transfer revocation coverage. Use the existing scoped recovery execution
PostgreSQL cases separately for pre-provider refusal.

Require distinct named scenarios in aggregate evidence; missing/duplicated cases,
nonzero side effects or generic terminal categories cannot qualify. A source stop
needs both import_blocked and source_path_unavailable. Keep identifiers, paths and
provider bodies out of public command summaries. Retain failed evidence and prove
project container/network/volume/workspace retirement after success and failure.

When a real fixture reveals missing runtime exhaustion, persist the stop in the
owning recovery transaction with terminal history, reputation and episode. Check
current search identity and cap, retain an already scheduled future search, and
test update/late-episode rollback plus replay. Do not manufacture terminal state
in fixture SQL to conceal an incomplete production path. Keep quality choices
separate from search exhaustion when their public status priorities differ.
