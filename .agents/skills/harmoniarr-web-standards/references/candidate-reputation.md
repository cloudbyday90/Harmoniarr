# Candidate outcome publication

Use when changing candidate delivery evidence, terminal recovery evidence or their replay behavior. Read the [design](../../../../docs/CANDIDATE_REPUTATION_DESIGN.md) and [research](../../../../docs/CANDIDATE_REPUTATION_RESEARCH.md).

1. Inventory each producer, its durable operation and every destination. Distinguish retrying an accepted observation from a genuine later attempt. Candidate identity alone conflates attempts; current producers use the guarded candidate event UUID for ledger and trust history. Preserve its database timestamp, including a PostgreSQL Date value.
2. Locate the owner of replay. Ordinary transitions use conditional status updates; recovery uses locked candidate/source-run episodes. Mint a fresh event-bound publication facade only after the guarded event insert. Refuse raw clients, foreign IDs, missing acknowledgements and expired scopes. A duplicate ledger primary key is a transaction failure, not successful replay.
3. Include all same-database effects in the producer transaction. Propagate the same connection through ledger and snapshot mutation; never checkout another client while holding the producer. READ COMMITTED precedes reads; producer locks precede shared snapshot admission and fresh snapshot read. Do not suppress SQL failure with a savepoint or detached callback. Preserve Error/null during rollback and release.
4. Keep evidence policy explicit. Applied imports succeed; terminal download/quality failures fail; an import blocker penalizes only an unavailable source. A scheduled same-candidate rejection retry and operator/environmental blocker do not penalize. Review recovery decision changes against these exclusions.
5. Keep database publication, external effects and advisories distinct. A rollback does not remove copied files or reverse remote downloads. Existing receipt/recovery guards must reconcile those effects. Run returned notification/auto-ignore work after commit; no exactly-once notification claim follows from ledger atomicity.
6. Prove replay after commit and after ledger pruning, distinct later attempts, independent concurrent calls, real SQL refusal, missing/foreign identity and process exit on both sides of commit. Verify server transaction retirement after child close before retry/cleanup. Assert results outside swallowed advisory adapters. The shared twenty-case registrar runs in isolated PostgreSQL and the guarded `validate:native-candidate-reputation` profile; pair it with existing spectral cross-writer and recovery transaction cohorts.

Ledger retention is not an idempotency receipt lifetime. Producer status/episode guards retain the supported replay boundary after pruning. Restores must retain coherent producer/evidence state; do not backfill ambiguous historical anonymous outcomes or replay a completed producer merely because its ledger event was pruned. Standalone injected projection tests do not establish producer authority or durable persistence.

Reuse existing minimal identifiers rather than retaining raw provider/file payloads. Discover/open official guidance through MCP; distinguish W3C privacy principles, PostgreSQL behavior and project inference. Prefer same-database transactions here; introduce an outbox only when an actual ownership/storage boundary requires one. Measure the full-snapshot rewrite before choosing a per-source migration.
