# Artist Detail Local and Operator Timing Design

Status: Implemented
Date: 2026-08-29
Owner: Metadata architecture + quality engineering

## Decision

Extend the existing real-browser Artist Detail cache proof with the two
same-origin requests that precede provider Discography for a locally known
artist:

1. local metadata lookup; and
2. operator-scoped projection.

The proof creates an isolated, locally known artist in its temporary
PostgreSQL database after the administrator session exists. It then captures
the actual browser resource timing for both authenticated application routes,
checks that the local response completes before the projection begins, and
confirms that a populated projection avoids the provider Discography fallback.
It retains the existing cold, fresh, and stale provider-SWR verification for
the unimported path.

No production telemetry, cache, endpoint, UI label, setting, user data store,
or browser storage is added.

## Why this is the next work

The prior browser proof established the server-to-browser SWR contract for
Discography and Related artists. The Artist Detail client intentionally
performs local lookup and, when available, operator projection first. Those
two requests can serially delay a local artist's catalog even when provider
SWR is correct. Measuring this real route path is the smallest way to decide
whether request orchestration needs a change.

The work preserves the multi-user model: the projection is requested through
the authenticated operator route after the admin session has been created. It
does not substitute a shared artist view for operator-scoped data.

## Standards and research review

Reviewed on 2026-08-29 against current primary sources:

- [W3C Resource Timing](https://www.w3.org/TR/resource-timing/) defines the
  `PerformanceResourceTiming` data used to measure same-origin `fetch()`
  requests, including the navigation-relative start and response completion
  timestamps. The test reads these values only after the matching response has
  completed and user-visible Discography content has rendered.
- [W3C Server Timing](https://www.w3.org/TR/server-timing/) defines the
  existing server-to-browser cache metric. It remains the correct evidence for
  provider-SWR state; local and operator requests use Resource Timing alone
  because they do not claim a provider-cache phase.
- W3C Resource Timing's security and privacy model restricts detailed timing
  exposure cross-origin unless a server opts in through `Timing-Allow-Origin`.
  The proof remains same-origin and adds no such header.
- [Playwright network guidance](https://playwright.dev/docs/network) supports
  waiting for the exact response generated by a browser action. The proof
  waits for each allowlisted route response instead of inferring individual
  request cost from a page-navigation total.

There is no visual-interface change in this increment, so W3C accessibility
patterns are not repurposed for performance diagnostics. The existing
progressive Artist Detail shell remains the user-facing accessibility measure;
this work only tests the underlying request path.

## Bounded evidence design

`buildArtistDetailRequestTimingEvidence()` accepts only the fixed
`local_metadata` and `operator_projection` endpoint labels and returns:

```json
{
  "endpoint": "operator_projection",
  "timing": {
    "clientRequestDurationMs": 7,
    "startTimeMs": 31,
    "responseEndMs": 38
  }
}
```

Values are rounded non-negative browser-relative milliseconds. The builder
rejects an unknown endpoint, missing timing, or a response completion that
precedes its own start. It never retains or reports an endpoint URL, artist
ID, local database ID, release title, payload, cookie, authorization value,
or response header.

The browser scenario asserts that the local response finishes before the
operator projection starts. It also checks that loading the locally known
artist does not add another provider Discography call, which protects the
projection-first fast path without assuming a particular duration threshold
from a developer machine.

## Options and trade-offs

| Option | Pros | Cons | Decision |
| --- | --- | --- | --- |
| Parallelize all three requests immediately | Could reduce an artificial local delay | Wastes provider work for a populated local projection and can compete with the shared provider queue | Reject without evidence |
| Add a production timing dashboard | Convenient ad-hoc visibility | Non-actionable for most home users; expands runtime data exposure | Reject |
| Use a browser fixture only | Fast and deterministic | Does not exercise authenticated routes, PostgreSQL reads, or the real operator service | Reject |
| Measure the real local/operator route path in an isolated browser scenario | Covers the serial client chain and operator scope without changing production | Requires browser/PostgreSQL integration infrastructure | Adopt |

## Security boundaries

- The temporary artist exists only in the isolated test database and is
  discarded with the scenario.
- Browser diagnostics contain only fixed endpoint labels and rounded relative
  timings; they omit identities, URLs, payloads, and session material.
- The normal authenticated routes, CSRF policy, multi-user operator scope,
  `Cache-Control: no-store`, and same-origin timing policy remain unchanged.
- The evidence adds no `Timing-Allow-Origin` response header and makes no
  external provider call.

## Final recommendation stack

1. Keep the local lookup → operator projection → provider fallback sequence;
   it avoids a provider fetch when the operator projection already contains
   the catalog.
2. Retain the existing provider-SWR test and add this local/operator timing
   proof as its companion guard.
3. Treat a repeated, reproducible local or operator latency regression as the
   trigger for a narrow query, projection, or concurrency improvement—not for
   a new cache layer or user-facing cache controls.
4. Preserve per-user operator projections and history; do not collapse them
   into shared metadata merely to shorten the request chain.
