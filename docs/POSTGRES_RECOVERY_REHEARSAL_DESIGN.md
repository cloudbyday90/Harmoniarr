# PostgreSQL recovery rehearsal design

Research and design date: September 11, 2026. Baseline: `a05cf59`.

## Decision and purpose

Add a generated-fixture PostgreSQL dump and restore rehearsal using one disposable Docker PostgreSQL 18 container. Prove that request recipients, collection decisions, release intents, retained provider work, and their constraints survive a real logical archive round trip. Exercise controlled continuation and ownership checks after restoration without starting Harmoniarr's application or workers.

The [provider access outcome](PROVIDER_ACCESS_ACCEPTANCE_OUTCOME.md) names this as the next independent release item. The [collection completion outcome](EXTERNAL_COLLECTION_COMPLETION_OUTCOME.md) establishes the durable ledger whose continuity needs proof. Existing [application backup design](BACKUP_RESTORE_DESIGN.md) and [administrator recovery runbook](ADMIN_RECOVERY_RUNBOOK.md) remain separate: the settings/wanted export does not preserve the complete request and job ledger, while bootstrap-admin recovery restores administrator access rather than a database snapshot.

This command accepts no existing database, deployment container, archive, or application endpoint. All database contents and encryption material are generated by the rehearsal. It adds no production restore route or browser button and does not operate on the running walkthrough database.

## Official research and implications

The following official sources were discovered through web search or links from discovered documentation, then opened through the web tool in September 2026.

| Source | Verified property | Design implication |
| --- | --- | --- |
| [PostgreSQL 18 SQL dump](https://www.postgresql.org/docs/18/backup-dump.html) | A logical dump is an internally consistent database snapshot despite concurrent ordinary writes. Restoring into an empty database based on `template0` avoids objects inherited from a customized template. | Use a full fixture dump and a fresh target. Database consistency does not establish consistency with media files or provider side effects. |
| [PostgreSQL 18 pg_dump](https://www.postgresql.org/docs/18/app-pgdump.html) | Custom archives support flexible restoration; `pg_dump` cannot dump a newer server major than its own. Archive output ignores the dump-time `--no-owner` option. | Use the source container's matching PostgreSQL tools and custom format. Apply ownership policy at restore time. Bound the wait for locks and do not depend on interactive password prompts. |
| [PostgreSQL 18 pg_restore](https://www.postgresql.org/docs/18/app-pgrestore.html) | Single-transaction restoration is all-or-nothing and implies exit-on-error; it cannot use parallel jobs. Ownership and grant restoration can be suppressed. Restoring an archive executes code selected by the source superuser, even for partial restores. | Choose serial atomic restoration of the small fixture. Skip ownership, ACLs, and tablespaces deliberately. Accept only the archive created during this run; these flags do not make arbitrary archives safe. |
| [PostgreSQL pg_dumpall](https://www.postgresql.org/docs/current/app-pg-dumpall.html) | Roles, tablespaces, and other cluster-wide objects require separate handling; `--globals-only` exports globals. | A single-database rehearsal does not prove cluster-role or privilege recovery. Document those as separate operator responsibilities instead of silently broadening the fixture. |
| [PostgreSQL 18 file system backup](https://www.postgresql.org/docs/18/backup-file.html) | File-level backup has different consistency requirements from a logical dump, including shutdown or a valid consistent filesystem snapshot. | Do not copy a live data directory and call it equivalent to this rehearsal. Media and volume recovery need their own proof. |
| [PostgreSQL 18 continuous archiving](https://www.postgresql.org/docs/18/continuous-archiving.html) | Point-in-time recovery combines a physical base backup with a continuous required WAL sequence. Logical dumps cannot be replayed with WAL. Configuration files are not recovered by WAL replay. | The rehearsal proves a logical snapshot restore only. It does not establish PITR, recovery-point objectives, WAL retention, or configuration recovery. |
| [PostgreSQL 18 password files](https://www.postgresql.org/docs/18/libpq-pgpass.html) and [libpq environment variables](https://www.postgresql.org/docs/18/libpq-envars.html) | PostgreSQL supports protected password files; real passwords in process environments can be exposed on some systems. Environment variables also influence connection defaults. | Never consume deployment credentials or implicit database connection defaults. The rehearsal uses a generated disposable secret passed to its child process environment, never command arguments or evidence. A real operator backup should use protected credential handling appropriate to its host. |
| [OWASP key management](https://cheatsheetseries.owasp.org/cheatsheets/Key_Management_Cheat_Sheet.html) | Losing the encryption key can make encrypted retained data unrecoverable; key backup needs independent protection. | Verify a generated encrypted secret with the same external key after restore and reject a wrong key. A database archive is not a backup of `HARMONIARR_SECRET_ENCRYPTION_KEY`. |
| [Docker port publishing](https://docs.docker.com/engine/network/port-publishing/) | Publishing without a host address exposes the port on host interfaces; explicit loopback binding narrows access. Docker versions before 28 have a documented same-L2 localhost-publishing caveat. | Bind the generated database to loopback and use a current Docker engine. Loopback binding does not replace password authentication or appropriate host/network controls. |
| [Node.js child processes](https://nodejs.org/api/child_process.html), checked against [Node 24 documentation](https://r2.nodejs.org/docs/latest-v24.x/api/child_process.html) | `execFile` runs an executable directly without a shell by default and supports timeouts, output bounds, and hiding Windows console windows. | Use bounded promisified `execFile` calls to Docker with argument arrays, `timeout`, `maxBuffer`, and `windowsHide`. Normalize process failures instead of retaining raw stderr. |
| [PostgreSQL versioning policy](https://www.postgresql.org/support/versioning/) and [18.6 release notes](https://www.postgresql.org/docs/18/release-18-6.html) | The current PostgreSQL 18 minor on September 11, 2026 is 18.6, released August 13; 18.5 was not released. PostgreSQL recommends the current minor, which includes security and correctness fixes. | Refresh the fixture image before release validation and record the actual server version and image ID. A mutable `postgres:18-alpine` tag or successful run against a cached image does not prove the current minor was tested. |

The recommendation to quiesce application workers is an application-level inference from the database snapshot boundary and Harmoniarr's job behavior. PostgreSQL does not require ordinary writers to stop for a consistent `pg_dump`; Harmoniarr must separately control side effects when deciding whether restored work may resume.

## Isolated execution contract

The ESM command is:

```powershell
npm run validate:postgres-recovery -- --evidence-path .tmp/postgres-recovery/rehearsal.json
```

The direct ESM entry point is equivalent:

```powershell
node scripts/validate-postgres-recovery.js --evidence-path .tmp/postgres-recovery-evidence.json
```

The output path must name a new evidence file. No `--live` flag is necessary because the command operates only on generated disposable data. There are no source/destination database, archive-input, production-container, or application-URL options.

The runner creates one owned disposable PostgreSQL 18 container with an explicitly loopback-bound port and a generated password passed through the child environment. Docker receives the environment variable's name, not its value, in process arguments. Before pulling or creating anything, the runner requires the effective Docker context and any `DOCKER_HOST` override to use a local Unix socket or Windows named pipe. Remote endpoints cannot create a container that the PostgreSQL client would then incorrectly reach through local loopback. The container mounts no host data, starts no application or provider client, and does not inherit a deployment database target. Connection details are explicit and refer only to this container. Before cleanup, verify the invocation's nonce label on the owned container; remove only that container and its owned anonymous volume. Pool closure has a five-second deadline so an unreleased client cannot prevent the owned-container cleanup attempt. Do not inspect for deletion, stop, or remove any existing running deployment container.

For release evidence, use a bounded fresh image pull without silently falling back to a stale local tag. The implemented fixture pins `postgres:18.6-alpine@sha256:d3e1620b530c944afa6e887d22eb899824da68e19c52024bf98f5220c88a65b2`, resolved by an actual Docker pull on September 11, 2026, and rejects a server version below `180006`. As of this design date, PostgreSQL 18.6 is the current minor. The [August security announcement](https://www.postgresql.org/about/news/postgresql-186-1711-1615-1519-1424-and-19-beta-3-released-3365/) includes fixes affecting PostgreSQL clients as well as the server; the [PostgreSQL 18 security table](https://www.postgresql.org/support/security/18/) identifies a `pg_dump` buffer overflow fixed in 18.6. The preliminary cached-18.3 smoke test was superseded by a full rehearsal against the pinned 18.6 image. Record the actual server version and image identity in every artifact; updating this fixture does not upgrade the running deployment or establish that future minor releases have been tested.

Within that container, the runner creates a source database from the repository's schema snapshot, verifies its stored migration checksums against the current migration manifest, and seeds deterministic scenario relationships with generated identities. It compares schema anchors before and after restoration. The restore target is a separately created empty database based on `template0`; it receives neither the application snapshot nor migrations before the archive restore. This verifies recovery of the current snapshot schema, while migration replay and upgrade compatibility retain their separate validation commands.

Create a full custom archive using the container's `pg_dump`, with `--no-password` and `--lock-wait-timeout=5s`. The archive stays under the container's generated temporary path. Restore through an explicit target database using:

```text
pg_restore --exit-on-error --single-transaction --no-owner --no-acl --no-tablespaces
```

Actual process arguments also contain the explicit generated connection and archive locations. Execute argument arrays directly without constructing shell commands. Do not use `--create`, which can select the database name stored in the archive, or `--clean`, which is unnecessary for the fresh target. Use bounded process and query waits with failure cleanup; dump or restore errors never become a pass because some rows are present.

This is a full logical PostgreSQL archive of the generated application database, not an expansion of the app-managed settings export. It therefore includes fixture user and retained job rows that the settings export intentionally excludes. It contains no real user, session, provider, or media data.

## Continuity scenarios and success criteria

Use two requests assigned to separate recipients. One carries a reviewed selection with an included release, a reasoned exclusion, and its retained discovery intent. The other remains in preparation with a completed page, retained continuation cursor, and queued work. Capture an exact canonical before/after snapshot of the relevant records; counts alone cannot prove that the same decisions and recipients survived.

Verify these properties after restoration:

| Property | Required evidence |
| --- | --- |
| Schema and relationships | Migration state, rows, foreign keys, decision reasons, revisions, intent ownership, and retained input/next cursors match the seeded source. |
| Stable work identity | Replaying existing work cannot create duplicate page or release-intent identity; uniqueness constraints still hold. |
| Controlled continuation | Injected collection services can continue the retained work against fixture responses, preserving committed decisions and target ownership. No real provider call occurs. |
| Request ownership | The two recipients remain isolated, and a restored intent cannot be reassigned merely because another request exists. |
| Accurate completion | A partially prepared or incompletely applied selection remains incomplete. Restoring rows is not evidence that acquisition finished. |
| External key dependency | A generated encrypted secret decrypts with its original generated key after restore. A wrong key fails, and neither key nor plaintext enters evidence. |
| Retained cancellation | Restored lease/run recovery preserves a cancellation request; recovery must not turn cancelled work into an automatically runnable retry. |

The source fixture must be stable while its before-state is recorded and dumped. The scenario deliberately starts no scheduler, HTTP application, or operation worker. Controlled post-restore service calls are injected with the target pool and fixture collaborators so default services cannot accidentally resolve the running deployment or contact providers.

The existing stranded-run recovery service can schedule retries when it finds missing or expired worker leases. Retaining a running row is therefore not permission to launch the normal application against a restored database. The cancellation regression addresses this behavior directly; the rehearsal does not claim that external effects can be replayed safely in every real recovery.

## Atomic failure proof

Create a third database owned by the rehearsal with a preexisting `media_requests` table. Attempt to restore the same generated archive into it using the same atomic restore flags. The table collision must cause failure, and the transaction must leave only the original table and its unchanged contents.

This checks a real restore failure after restoration has begun, rather than only rejecting a corrupt archive header. It is a negative verification scenario, not permission to restore into any preexisting operator database. Failure to observe both the expected error and unchanged target state fails the rehearsal.

## Evidence and security boundaries

The persisted evidence is an explicit allowlist of schema/version metadata, bounded counts, verification booleans, PostgreSQL version, Docker image identity, and the generated archive's SHA-256. The checksum identifies the bytes tested; it is not an authenticity guarantee for an arbitrary archive.

Do not persist database/container credentials, connection URLs, host paths, fixture record IDs, raw rows, encryption keys, plaintext, provider responses, SQL output, or raw subprocess errors. Report stable stage-specific failures. Keep the generated database archive inside the disposable container; the host artifact is the sanitized rehearsal result, not a downloadable database backup.

Do not overwrite existing evidence. A failed restore, mismatched state, failed domain assertion, or failed owned-resource cleanup must not be described as successful recovery. Artifact provenance must clearly identify generated fixtures and isolated Docker execution so it cannot be confused with a real operator restore or a production backup assessment.

No browser interface is added. Existing Settings recovery and bootstrap-admin interfaces retain their current native controls and authorization boundaries. This CLI does not require new W3C interaction patterns or unrelated browser tests.

## Alternatives and tradeoffs

| Option | Pros | Cons | Decision |
| --- | --- | --- | --- |
| Extend the settings/wanted export to copy every runtime table | One familiar recovery surface | Changes its authentication and transient-state contract; still needs database consistency and side-effect handling | Defer |
| Compare SQL fixtures before and after insertion | Fast and deterministic | Does not exercise archive tools, restoration order, indexes, or real failure rollback | Keep only as lower-level coverage |
| Generated full custom dump and atomic restore | Exercises real PostgreSQL tools, complete relationships, and all-or-nothing failure without deployment data | Requires Docker; does not prove production volume, role, or external-provider recovery | Choose |
| Restore an operator backup through a new application button | Directly tests a real environment | Introduces executable archive input, database replacement, credential restoration, and worker-replay risks | Outside this scope |
| Physical base backup plus WAL rehearsal | Supports PITR and lower potential data loss | Requires complete WAL retention, physical compatibility, configuration recovery, and a separate operating procedure | Separate follow-up when recovery objectives require it |
| Parallel restoration | Faster for large databases | Incompatible with the selected single-transaction guarantee and unnecessary for this fixture | Defer |

## Operator recovery boundaries

The rehearsal is release evidence for database continuity. A real operator recovery still needs a trusted archive, known compatible PostgreSQL tools, protected role/configuration recovery, the original external encryption key, media/download volumes as appropriate, and a separately verified destination.

Keep application workers and provider side effects quiesced during real restoration and validation. Review restored authentication/session state, outstanding transfers, cancellation requests, leases, and already-completed external actions before permitting work to resume. Restoring an older database cannot undo a provider request or file operation that happened after the snapshot. These deployment procedures are not performed by the rehearsal.

`--no-owner`, `--no-acl`, and `--no-tablespaces` are intentional fixture portability choices. Success under these flags does not prove preservation of deployment roles, grants, ownership, or tablespace layout. Likewise, successful decryption with a generated test key does not prove that an operator has retained the key for their own database.

## Final recommendation stack and validation

Use Node 24 LTS and modular ESM orchestration, fixture, verification, and evidence modules. Use an owned PostgreSQL 18 Docker container with matching dump/restore tools, a full custom archive, a fresh `template0` target, atomic restore flags, exact continuity comparisons, and controlled service-level recovery assertions. Keep secrets external and evidence allowlisted.

Run focused script/fixture and retained-cancellation tests, then execute the isolated Docker rehearsal. Add an independent Repository Validation job that runs the command and uploads only the allowlisted JSON evidence through the existing pinned artifact action. Because the exact artifact path is under `.tmp`, enable `include-hidden-files` for that single file; [the official action documentation](https://github.com/actions/upload-artifact#uploading-hidden-files) excludes dot-directory contents by default. Never widen this upload to the entire temporary directory. Its PostgreSQL 18 fixture matches the deployed database major; existing PostgreSQL 17 validation jobs remain unchanged. Run the repository validation stack for the final patch. Record actual commands, pass/fail results, PostgreSQL/image identity, and remaining limitations in a separate outcome document; merely adding the command does not prove restoration.

The next independent code item after a successful rehearsal is Music Queue pagination and preparation progress. Before release, also capture immutable-image fresh-install and upgrade evidence, including migration compatibility and the packaged recovery environment. Real provider acceptance remains a separate outstanding item until an operator enables a saved connection and supplies usable access. Consider production-scale restore timing, protected key recovery, and physical/WAL recovery only against explicit recovery objectives. The separate [outcome document](POSTGRES_RECOVERY_REHEARSAL_OUTCOME.md) records execution and the updated recommendation order.
