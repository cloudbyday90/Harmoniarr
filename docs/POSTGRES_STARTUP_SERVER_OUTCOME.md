# PostgreSQL server startup evidence outcome

Fresh default PostgreSQL 18 Alpine fixtures now provide failure-only structured
server startup evidence for an original unnamed, matched client. Four narrow ESM
modules own configuration, log classification, public records and read-only
capture. Existing runtime, driver observer, direct pool and both app entrypoints
forward the private accepted context into canonical failure completion. See the
[design](POSTGRES_STARTUP_SERVER_DESIGN.md) and
[official research](POSTGRES_STARTUP_SERVER_RESEARCH_2026_10.md).

## Behavior and security boundaries

The container enables receipt/authentication/authorization/setup JSON logging,
English messages and verbose source locations only under fresh default ownership
with both diagnostics enabled and the reviewed image family. External, reused,
custom and unsupported configurations retain their existing path. The existing
pg 8.23.0/pg-pool 3.14.0 internal adapter version checks remain.

The adapter captures descriptors of a plain non-proxy startup packet, preserves
explicit application names and unsupported accessors, and adds a random private
marker only to an otherwise unnamed packet with the acknowledged user/database.
Original credentials, other startup options, method receiver/result and Error/
null remain. Its method/listeners and private context are removed at settlement.
The failure boundary captures that context once before scheduling probes, after
registering its canonical completion, so later caller mutation cannot redirect
the accepted match.

Only a complete, unique marker-bearing authorization record with exact private
user/database binds a server PID/session to the original client. Recognized
source locations and ordered session line numbers then select earlier receipt/
authentication and initial ready/setup. Query-generated lookalikes, foreign
sessions, duplicate markers/line numbers and reversed stages cannot become proof.
Partial or malformed rows are excluded with clipped-window reporting. Association
is within the bounded window, not a claim of complete server history.

The original client ID and checkout ID link the fourth-version failure record to
existing client milestones. Public startup fields are fixed flags, bounded counts,
approved stages and numeric setup/fork/authentication durations. Raw log rows,
markers, usernames, database names, socket addresses, PID/session keys, paths,
query text and credentials are not published. Explicit names or unsupported/
unobserved clients retain existing records without fabricated server association.

The probe reads the captured immutable container's known JSON file, at most
65,536 bytes and 256 bounded rows, through hidden read-only argv with a two-second
command limit. Every observation settles before forwarding the original failure
or closing pools/container. Successful default checkouts launch no extra probe.
Startup markers/logging still have observer overhead. Temporary logs grow during
the owned container's lifetime, and the logging collector changes direct Docker
stderr visibility; read/output bounds are not a disk cap.

## Preserved rejected candidates

The first native candidate passed named-client behavior but failed the three
association/receipt controls. The initial parser assumed explicit `00000` on
ordinary LOG rows. PostgreSQL's reviewed jsonlog source omits the zero SQLSTATE;
accepting only its omitted/zero form corrected that source contract.

The next candidate associated authorization/ready, but failed early-receipt
controls. A separate private inspection emitted only structural keys and
approved metadata/comparison flags: the actual receipt backend type was `not
initialized`, while later stages identified a client backend. The parser now
permits that early type only at the reviewed receipt location. Full association
assertions were preserved and the reviewed four-case candidate passed.

Late focused review also exposed a disabled-startup probe returning undefined,
which omitted its expected unavailable field. The capture now reports explicit
unavailability while launching no log read. Final context capture, accessor and
public-record refinements preceded the final frozen native/fast gates. Both
rejected native logs, the rejected focused log and earlier passing scope are
retained separately. No resource bound, retry policy or deadline changed.

## Recommendation and next work

Adopt fresh owned structured capture, private marker/session association and
canonical failure drainage; retain explicit unknown/clipped outcomes and existing
resource policy. Pros are precise server/client stage evidence with minimized
output. Costs are temporary logging, marker preparation and bounded capture work
on failures. Pre-authentication identity remains unknown when authorization never
logs the marker; NAT tuples and later healthy probes cannot fill that gap.

The [historical source-noop matrix](WANTED_SOURCE_NOOP_OUTCOME.md) remains
incomplete and its cause unknown. It was not replayed here: these diagnostics
changed, but Wanted algorithm/hash work did not. Next collect a fresh, separately
labeled guarded workload to capture any recurrence under the new evidence before
changing pool policy or scheduling. Then design guarded no-change Wanted/link
publication, retaining writer/absent-row proof and final complete byte authority.

records a new collection under this instrumentation and its own command changes.
