# Music Queue Provider Handoff Confirmation Design

## Status

Implemented on 2026-08-25.

## Problem

Sending selected Music Queue files to slskd is a provider-side `POST`. Before
this change, Harmoniarr only wrote the accepted transfer identifiers after the
provider call returned. A process crash or lost response in that interval made
the outcome unknowable. Retrying the `POST` could create duplicate downloads.

## Research basis

- [RFC 9110, HTTP Semantics](https://www.rfc-editor.org/rfc/rfc9110.html)
  states that a client should not automatically retry a non-idempotent request
  unless it knows the original request was not applied or otherwise knows the
  request is idempotent.
- slskd’s official
  [configuration documentation](https://github.com/slskd/slskd/blob/master/docs/config.md)
  says its OpenAPI definition is generated by enabling Swagger on the running
  instance. The published provider documentation does not establish a stable
  client-supplied idempotency-key contract for download enqueue.
- The official [slskd repository](https://github.com/slskd/slskd) documents a
  download queue that can be inspected, cancelled, retried, and cleared. That
  makes read-after-write confirmation practical for a self-hosted deployment.

## Options considered

| Option | Benefits | Costs / risk |
| --- | --- | --- |
| Repeat the enqueue request after a timeout or crash | Simple and fast | Can duplicate transfers; conflicts with HTTP retry guidance. |
| Require an slskd idempotency key | Cleanest external contract if supported | No documented, portable contract is available today. |
| Add a general outbox, broker, and distributed coordinator | Strong foundation for many future integrations | Excessive operational complexity for a single-node home-hosted application. |
| Durable checkpoint plus exact provider confirmation | Prevents automatic duplicate requests; uses existing PostgreSQL and provider read API | A genuinely ambiguous result remains visible until slskd can confirm it or the operator chooses a different match. |

## Recommendation stack

1. Persist the exact filename-and-size request in the existing execution-run
   item before calling slskd.
2. Treat the post-checkpoint result as unconfirmed until Harmoniarr persists
   the provider response.
3. On restart, list that source user’s downloads and accept a prior request
   only when every requested filename and byte size matches exactly.
4. Never automatically re-send an unconfirmed request. Block a new download
   run while the selected match has an unconfirmed handoff.
5. Show a specific “Confirming download request” status and an actionable
   instruction to sync Downloader rather than presenting a generic failure.

## Implementation boundaries

The design deliberately reuses `import_execution_run_items`; it does not add a
message broker, a distributed lock, a second database, or a cloud dependency.
It is therefore appropriate for the supported single-node Compose topology.

The confirmation match is intentionally strict:

- provider username is part of the request scope;
- remote filename is normalized only for slash direction;
- byte size must match;
- each provider transfer can satisfy at most one requested file.

An incomplete match remains unconfirmed. This favors avoiding duplicate
downloads over silently assuming that a missing provider row means the POST
was not applied.

## Security and privacy

- The durable snapshot contains only source username, filenames, sizes, and
  provider transfer metadata already required by the Music Queue workflow.
- It stores no provider API key, authorization header, or raw HTTP response.
- The existing authenticated, CSRF-protected Music Queue routes remain the
  sole way to start a run.
- The server’s existing outbound URL and provider-key protections remain
  unchanged.

## Validation plan

- Unit-test exact filename-and-size confirmation.
- Unit-test a resumed worker confirming a handoff without a second enqueue.
- Unit-test an unresolved handoff that remains visible and blocks a new run.
- Run the full repository validation and the documented local Compose rebuild.
