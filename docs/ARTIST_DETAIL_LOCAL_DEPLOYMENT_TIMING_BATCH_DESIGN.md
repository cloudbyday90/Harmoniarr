# Artist Detail Local Deployment Timing Batch Design

Status: Implemented
Date: 2026-08-30
Owner: Metadata architecture + quality engineering

## Decision

Extend the existing one-shot local Artist Detail measurement with a bounded
repeat-run mode. The administrator can capture two to five sequential,
read-only visits for the same local artist and receive a safe comparison
artifact alongside the individual safe samples.

The default remains one visit. `--runs 3` is the recommended first comparison:
it is enough to expose a repeated route outcome or an obvious outlier without
turning a home-hosted diagnostic into a prolonged synthetic workload.

This is a diagnostic improvement only. It does not change Artist Detail cache
policy, request concurrency, browser storage, API contracts, user-facing
controls, data ownership, or acquisition behavior.

## Why this is the next work

A single local browser capture identifies the active request path, but cannot
distinguish a repeatable delay from a one-off host condition. The cache report
must be evidence-led: first establish whether the same local projection or
provider fallback path occurs repeatedly, then make a focused regression at
the slowest confirmed leg.

The new batch contract keeps the comparison narrow. It neither makes a
performance dashboard nor emits telemetry. A household administrator runs it
only for a reproducible report and keeps the evidence on the deployment host.

## Standards and research review

Reviewed on 2026-08-30 against current primary sources:

- [W3C Resource Timing](https://www.w3.org/TR/resource-timing/) defines a
  browser resource-timing model with navigation-relative values. Its security
  and privacy sections restrict detailed cross-origin timing by default, which
  supports retaining only same-origin, bounded measurements here.
- [W3C Server Timing](https://www.w3.org/TR/server-timing/) standardizes
  server-supplied performance metrics when a server chooses to expose them.
  Harmoniarr retains the existing provider-cache evidence rather than adding a
  broad new timing header to every local request.
- [Playwright request timing](https://playwright.dev/docs/api/class-request#request-timing)
  makes `responseEnd` available after a request finishes and specifies that
  `startTime` is absolute. The existing collector converts those values to
  bounded capture-relative milliseconds before any artifact is built.
- [Playwright network monitoring](https://playwright.dev/docs/network)
  supports observing the requests generated by a real browser navigation.
  The batch reuses that exact authenticated route rather than substituting an
  unauthenticated HTTP probe.

There is no normal-user interface in this increment. W3C accessibility
principles therefore guide the decision not to add unexplained operational UI
to Artist Detail: the administrator uses a documented command with explicit
inputs and output, while the product remains focused on music tasks.

## Design

`scripts/artist-detail-local-timing-batch-evidence.js` owns the new aggregate
schema. `scripts/measure-artist-detail-local-timing.js` remains the small
orchestrator and invokes the existing one-visit measurement sequentially.

Each run opens a new browser context, blocks service workers, signs in through
the normal form, and visits only the same loopback Artist Detail URL. A new
context prevents browser-session cache state from being carried across samples.
The deployment's normal server and application caches remain intact on purpose:
the result represents repeated local use, not an artificial cold-server load.

For two to five samples, the aggregate retains only:

| Field | Purpose | Privacy boundary |
| --- | --- | --- |
| `samples` | Existing allowlisted one-visit artifacts | Fixed endpoint categories, status families, and rounded relative timings only |
| `outcomeCounts` | Counts each allowed route outcome | No artist, user, provider, or cache key |
| `outcomeIsConsistent` | Shows whether every run used one route outcome | Boolean only |
| `endpointTimings` | Minimum, P50, P95, and maximum per observed endpoint | Rounded milliseconds, no URL, headers, body, or exact status |

The P50 and P95 values use linear interpolation over the sorted rounded sample
values. With at most five runs, P95 is a high-end comparison signal—not a
population percentile or an automated alert threshold.

The aggregate is reconstructed and checked against its samples before it can
be written. Unexpected fields and altered summaries are rejected.

## Security and multi-user boundaries

- The command retains its loopback-only base URL, file-only password input,
  workspace-only evidence path, and read-only browser navigation.
- Each sample stays within the allowlisted schema. The batch cannot add an
  artist identifier, user identity, username, URL, request/response body,
  cookie, header, credential, or absolute request clock through aggregate
  fields. The later schema-version-2 presentation extension adds only fixed
  state labels and rounded navigation-relative observation time; see [Artist
  Detail Local Presentation Timing Design](ARTIST_DETAIL_LOCAL_PRESENTATION_TIMING_DESIGN.md).
- The authenticated operator projection remains scoped to the account used for
  the capture. A batch does not combine or expose projections across users.
- Runs are sequential and capped at five. They do not add parallel provider
  load, alter a request, or attempt cache invalidation.
- The evidence is printed locally or written only to a selected path under the
  repository. It is not sent to an external telemetry service.

## Use

After reproducing a slow Artist Detail visit, run three samples using the
account whose experience is being investigated. Do not commit the password
file or the optional evidence artifact.

```powershell
npm run measure:artist-detail-local-timing -- -- `
  --artist-mbid 01234567-89ab-cdef-0123-456789abcdef `
  --username local-admin `
  --password-file C:\secrets\harmoniarr-password `
  --runs 3 `
  --evidence-path artifacts\artist-detail-local-timing-batch.json
```

`HARMONIARR_ARTIST_DETAIL_TIMING_RUNS` provides the same bounded optional
input. Omitting it, or passing `--runs 1`, returns one version-2 single-sample
artifact; values from two through five return the corresponding version-2
batch artifact. Values outside one through five are rejected.

With npm 12, retain both separators after the script name: the first ends npm
option parsing and the second starts arguments for the ESM script. This was
verified against the local walkthrough on 2026-08-30.

## Options and trade-offs

| Option | Pros | Cons | Decision |
| --- | --- | --- | --- |
| Change cache/concurrency based on one report | Fast to implement | Cannot distinguish a repeated bottleneck from an outlier; can add redundant provider work | Reject |
| Capture three sequential local visits | Shows outcome consistency and high-end timing while retaining a small operational footprint | Does not simulate a cold server or multiple concurrent users | Adopt |
| Add always-on timing telemetry or a dashboard | Continuous visibility | Non-actionable for ordinary home users; increases operational-data exposure | Reject |
| Export unrestricted browser trace/DevTools data | Rich investigation data | Can retain URLs, response metadata, and account context | Reject |

## Final recommendation stack

1. Capture three local visits under the affected account with `--runs 3`.
2. If all outcomes are `local_projection`, investigate the slowest of local
   metadata or the per-user projection service; do not make a provider change.
3. If provider fallback is consistent, compare the existing provider
   `Server-Timing` cache-phase evidence before altering provider-SWR behavior.
4. If outcomes vary, first establish why the current local projection is not
   consistently usable; do not mask that state with eager parallel browsing.
5. Add one focused regression beside the confirmed responsible service before
   changing production behavior.
