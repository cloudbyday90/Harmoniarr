# Music Queue Match-Selection Idempotency Design

## Status

Implemented 2026-08-24.

## Problem

Selecting a Music Queue match changes durable import-candidate state, records
the decision, and may begin download work. The client already prevents a
second click in one view, and the shared selection guard prevents different
candidates from being selected concurrently. Neither lets a caller safely
learn the result when the selection succeeded but its HTTP response was lost.

Harmoniarr already owns a durable, actor-scoped control-plane idempotency
record with a response body, status code, request hash, expiry, unique
constraint, and scheduled expiry cleanup. Music Queue did not yet use it.

## Research

Research was reviewed on 2026-08-24 against these official sources.

- The IETF's latest `Idempotency-Key` work describes a client-generated key,
  a request fingerprint, a defined expiry policy, replay of a completed result,
  and a conflict for an in-progress duplicate. The document is an **expired
  Internet-Draft**, not a published RFC, so it informs this design rather than
  defining a protocol requirement. [IETF document status](https://datatracker.ietf.org/doc/draft-ietf-httpapi-idempotency-key-header/) and [draft text](https://datatracker.ietf.org/doc/html/draft-ietf-httpapi-idempotency-key-header-07)
- HTTP protocol design guidance says not to redefine the semantics of an
  existing header. This design uses the established `Idempotency-Key` name and
  does not invent a Harmoniarr-specific replacement.
  [RFC 9205 §4.7](https://datatracker.ietf.org/doc/html/rfc9205#section-4.7)
- PostgreSQL row locks block competing writers until a transaction ends. The
  existing shared-selection guard remains the authoritative protection for
  simultaneously choosing candidates; a response cache is not a replacement
  for that invariant. [PostgreSQL explicit locking](https://www.postgresql.org/docs/current/explicit-locking.html)

## Options

| Option | Benefits | Costs | Decision |
| --- | --- | --- | --- |
| Keep the browser single-flight gate only | No server change. | Cannot recover a lost response or protect another process. | Reject. |
| Add a Music Queue-specific idempotency table | Can be tailored to one route. | Duplicates the existing durable record, cleanup, and hashing lifecycle. | Reject. |
| Reuse the control-plane idempotency service at the route boundary | Durable replay, actor isolation, request fingerprinting, 48-hour expiry, no migration, and no large service. | Completed requests replay only after their record is written; the shared selection guard still handles simultaneous competing work. | **Adopt.** |
| Require an idempotency key from every caller immediately | Enforces the strongest client contract. | Breaks direct self-hosted API callers that do not yet send a key. | Defer until the public mutation contract is formalized. |

## Contract

The authenticated `POST /api/v1/acquisition/releases/:wantedReleaseId/matches/:matchId/use`
route now passes the request through the existing idempotency service.

| Concern | Contract |
| --- | --- |
| Header | The browser sends a fresh `Idempotency-Key` generated by the existing client utility. If a use-match request has no confirmed HTTP response, the Music Queue composable retains that key for the next attempt of the same match; it clears the key after a confirmed response. The server remains backward compatible when the header is absent. |
| Scope | `acquisition.musicQueue.matches.use` |
| Isolation | The durable lookup key is the scope, authenticated actor ID, and idempotency key. A key from one household user cannot replay another user's response. |
| Fingerprint | `wantedReleaseId`, `matchId`, and the optional decision `reason`. Route metadata, cookies, CSRF tokens, peer data, and IP address are excluded. |
| Retention | The existing service retains successful results for 48 hours and its existing hourly cleanup removes expired records. |
| Completed retry | A matching key and fingerprint returns the stored status and payload without invoking selection or recording another selection audit action. |
| Changed payload | The existing service returns `409 idempotency_key_payload_mismatch`. |
| Concurrent choice | The shared discovery-request selection guard remains authoritative and returns its generic conflict without exposing another candidate or user. |

The fresh-session and CSRF checks run before the idempotency lookup. Release
ownership is still established inside the Music Queue pipeline before the
candidate transition. Consequently, possessing an old key alone cannot bypass
authentication, a fresh login, CSRF validation, or release scoping.

## Implementation

1. `createApp` creates one shared control-plane idempotency service instance
   and supplies it to both the existing system module and the acquisition
   module.
2. The acquisition module exposes the injected execution function only to its
   route boundary; the pipeline service remains responsible for release
   ownership and candidate selection.
3. The use-match route hashes the trusted route IDs plus the operator-supplied
   reason, executes the normal pipeline only for a first request, and returns
   either the new or stored result using the original status code.
4. A small ESM retry-key store retains a scoped client key only between an
   unconfirmed transport failure and the next attempt of the same selection.
   The API client uses the existing `control-plane-idempotency` utility for the
   header. No CommonJS code or global singleton was added.

## Security and privacy

- The idempotency record stores a SHA-256 request hash rather than the request
  inputs. The free-text reason therefore is not copied into that record.
- The database unique key includes the actor identity and operation scope,
  preventing cross-user and cross-operation replay.
- Existing fresh-session, CSRF, rate-limit, release-ownership, candidate
  selection, transaction, and audit boundaries are retained.
- The stored response contains the same user-authorized payload that the
  original route would return; it does not reveal the competing candidate
  identity used by the shared selection guard.

## Verification

- Route coverage proves the correct actor, scope, header key, and fingerprint
  are delegated only after fresh-session and CSRF validation.
- Route coverage proves a stored result bypasses the selection function.
- Client coverage proves use-match sends the CSRF token and a scoped
  `Idempotency-Key` header, while the retry-key store and Music Queue
  composable coverage prove an unconfirmed selection reuses that key.
- Existing idempotency-service coverage continues to prove durable replay,
  expiry, payload mismatch, actor scoping, and key length bounds.

## Recommendation stack

1. **Delivered:** durable completed-response replay for Music Queue match
   selection, layered on the existing shared-selection guard.
2. **Keep:** browser release single-flight and post-conflict SWR revalidation;
   they improve operator feedback but are not correctness mechanisms.
3. **Next:** evolve the shared idempotency service to reserve an in-progress
   key atomically if Harmoniarr must give same-key concurrent retries a
   protocol-specific `409` instead of relying on the selection guard's
   resource conflict. Do this generically, with a migration and recovery
   policy, rather than creating one Music Queue-only table.
